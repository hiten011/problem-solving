Problem: [Inchworm]

Design Thinking:
The problem told us to find out the number of times the Inchworm hits the leaf. I initially thought of running a for loop and checking if that position contains a leaf or not, this would have resulted in a O(n) solution, which was working. However, I realised the leach and the leaf are meeting after set intervals, that means if I can find out the interval of their first meeting point, then that interval would be respected and they meet after same interval. Also, I realised that interval can be found by finding the lcm() of the leaf and branch as it gives me the least common multiple of both which is basically what I need here.

Troubleshooting:
As 0 contains the leaf I need to consider that leaf in my answer so I return the answer as +1.

Reflection:
Realised that identifying repetitive meeting intervals can reduce time complexity significantly and that LCM can be used to find the exact meeting cycle instead of simulating every step.

Problem: [StreetParking]

Design Thinking:
The problem asks us to find the number of places where we can park the car. We can do that by just simply looping through the street and blocking the spaces by marking them as X. So what I am doing is I am just looping and marking the places as X in which I cannot park the car, this takes O(N) time complexity.

Troubleshooting:
I got a wrong answer for one of the test cases. I realised that, if I update the forward spaces as well they might result in incorrect solution, as my above method won’t work with DB input. D makes the B X, so I need to be careful when changing the forward statements. That can be simply done by keeping track of how many forward spaces do I need to mark as X, and I can do it at last. I am changing the code such that when I encounter a street, I will make my forward street X only in the case if the front is a -, otherwise I won't do it.

Reflection:
Learned that updating state while iterating can cause incorrect results if dependencies exist between elements ahead. Deferring updates until after checking all necessary conditions can prevent these errors.


Problem: [CircularLine]

Design Thinking:
The brute force method I thought of doing was, by calculating the distance from each point to each point from forward and backward I can calculate all the possible paths, and keeping the fastest from each point, then finding the max would give me my answer. But that would take O(N³) solution, and I am calculating each subarray distance. However, I think I can optimise it further by using prefix sum.

Troubleshooting:
By using prefix Sum I optimised my code to O(N²), because I don’t need to calculate distance each time now, as the distance can be easily calculated in O(1) time. I am thinking can we solve this problem with O(N) time using sliding window approach, I will try that idea out. Yes it works — I am increasing the size of window when the forward distance is smaller than back distance as I would need to make it greater to get maximum answer, and then vice versa in case of my back distance, I am increasing my start pointer. This is all possible because the constraints given say the distance is always positive, which means the result will only increase if the width increases.

Reflection:
This problem showed me the progression from brute force → prefix sums → sliding window. Also, recognising positive constraints allowed me to safely apply a window-expansion strategy for an O(N) solution.
