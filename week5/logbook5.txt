Problem: [TomekPhone]

Design Thinking:
I needed to minimize keystrokes when assigning letters to keys. If the total number of slots was less than the number of letters, I returned -1. Otherwise, I sorted frequencies in descending order and assigned the most frequent letters first, cycling through keys while tracking how many presses each key already had.

Troubleshooting:
Initially, I missed multiplying frequencies by the press depth, which gave wrong results. Adding a counter (numKeys[idx]) fixed this by correctly accounting for how many times a key had been pressed.

Reflection:
Sorting and greedy allocation reduced the problem to O(M log M). I learned how careful ordering of tasks (highest frequency first) can greatly simplify weighted cost problems. TC: O(mlogm+m⋅n)


Problem: [HouseBuilding]

Design Thinking:
The task is to minimize the total cost of leveling buildings represented by digits. I stored the frequency of each digit (0–9) and then used a two-pointer approach. Starting from both ends, I repeatedly shifted the smaller frequency towards the middle, adding the cost along the way. This way, all values eventually converge to the same height.

Troubleshooting:
At first, I considered brute force by testing every possible target height and summing costs, but this would have been inefficient. The frequency compression with two pointers gave a more direct and efficient way to simulate the leveling process.

Reflection:
This solution runs in O(N) for processing the grid and then O(10) for balancing heights. I learned that when a problem involves “leveling” or “equalizing,” working with frequencies and merging from extremes can simplify the approach compared to brute force. TC:O(N)


Problem: [NumberSplit]

Design Thinking:
The goal was to find the longest sequence starting from a given number, where each step splits the number into factors. I used dynamic programming (dp[i]) to store the longest sequence length for each number up to start. For each number, I needed to generate all possible products of splits of its digits and then transition to those states.

Troubleshooting:
Initially, I only split numbers into two parts, which failed on test cases where numbers could be split into more than two parts. This made me realize that I needed to consider all possible splits of a number, not just two. To handle this, I used recursion with bitmasking (2^D possibilities, where D = number of digits) to enumerate every valid split and calculate products. Once I fixed this, I updated dp[i] by checking transitions from all products.

Reflection:
This problem was tricky because of the exponential number of digit splits. However, combining recursion for split generation with DP for sequence length gave me an efficient-enough solution. I learned the importance of carefully reading problem constraints — overlooking the possibility of multiple splits initially caused me to miss valid cases.
TC: O(N * D * 2 ^ D):- [D = log(N): number of digits in N]


Problem: [RGBStreet]

Design Thinking:
The task is to minimize the cost of painting houses, with the constraint that no two adjacent houses have the same color. I used bottom-up dynamic programming where dp[i][c] stores the minimum cost to paint houses from i onwards, starting with color c. The transition is dp[i][c] = cost(c) + min(dp[i+1][other colors]).

Troubleshooting:
At first, parsing the input costs from strings was a bit tricky since each house's costs came in one line. I solved this with a helper function getCost() that splits the string into integers. Once parsing was fixed, the DP logic worked smoothly.

Reflection:
This problem reinforced the idea of breaking down a DP state into "choice + constraint". Handling the parsing separately also kept the DP logic clean. The final solution runs in O(n) with constant space per house, which is efficient.

Main Themes:
This week I tackled a mix of greedy, dynamic programming, and frequency-based problems. A common theme was balancing efficiency with correctness — whether through sorting, compressing states, or enumerating splits.

Key Learnings:
Greedy works when tasks have clear priority: In TomekPhone, assigning highest-frequency letters first minimized cost.
Frequency compression simplifies equalization: In HouseBuilding, simulating merges from extremes avoided brute force.
Don’t overlook problem constraints: NumberSplit taught me that considering only two splits wasn’t enough; fully enumerating splits was required.
DP is about “choice + constraint”: RGBStreet reinforced that states and transitions must carefully encode constraints (like adjacent colors).

Reflection:
I noticed a pattern where my first attempt was too narrow (e.g., missing multiplications in TomekPhone, missing multi-splits in NumberSplit). Slowing down to think about all constraints upfront could save time. On the other hand, once the direction was right, implementing clean helper functions (like parsing costs in RGBStreet) made the solutions much easier to debug and reason about.
